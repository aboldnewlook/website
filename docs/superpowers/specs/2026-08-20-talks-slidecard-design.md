# /talks — the Slidecard deck framework

Date: 2026-08-20
Status: design, awaiting review. No implementation has begun.

## 1. Context

`aboldnewlook.com` should host presentations. The visual and interaction
design comes from a Claude Design mockup, "Deck presentation framework UI
mockup" (project `6210deee-9762-49ed-825f-a330e74889c7`), file
`Slidecard Framework.dc.html`: a card on a wallpaper backdrop, slides laid
out on a 2D map, and a camera that flies between them.

The mockup is **not** a shippable artifact. It is a `.dc.html` canvas
document whose sibling `support.js` is a 72 KB generated runtime that loads
React 18.3.1, ReactDOM, and Babel standalone from unpkg at page load, then
interprets `x-dc` / `sc-for` / `sc-if` / `{{ }}` templates through a
`DCLogic` class. Shipping it would break all four claims in the first
paragraph of the README at once. The mockup is therefore treated as a
**design reference**, and its behaviour is reimplemented natively.

## 2. Goals

- A deck is a readable, linkable, crawlable web page with JavaScript off.
- With JavaScript on, the same page becomes the Slidecard player.
- Good enough to present from live, on unreliable conference networks.
- Each presentation can carry its own theme and wallpaper.
- No build step. `wrangler deploy` stays the whole pipeline.

## 3. Non-goals

- Speaker notes, presenter view, or a second-screen mode.
- Authoring UI. Decks are files, edited in an editor, committed to git.
- Slide transitions beyond the camera fly (no per-element builds).
- PDF export.

## 4. Decisions

| # | Decision | Rationale |
|---|---|---|
| D1 | Reading is primary; the player is a progressive enhancement | A deck must survive as a web page. Presenting is the secondary mode. |
| D2 | Decks are markdown files in the repo, bundled by a wrangler `Text` rule | No new D1 binding; decks are versioned with the code; `wrangler deploy` unchanged. |
| D3 | Slide position is authored explicitly as `pos: x,y` | Chosen over deriving coordinates from heading depth. Costs hand-maintained bookkeeping, which §10 mitigates with validation. |
| D4 | Document order is the sequence; `pos` is only for arrow navigation | The two may deliberately disagree. |
| D5 | Theme is a fenced ` ```css theme ` block inside the deck file | A fixed token vocabulary cannot express the mockup's own backdrop (a 3-stop radial gradient, a 115° hatch, and a dot grid). Raw CSS is simultaneously simpler and more powerful, and keeps a deck one portable file. |
| D6 | System fonts by default; Google Fonts opt-in per deck via frontmatter | Zero external requests unless a deck asks. Declared in frontmatter, not CSS `@import`, so the Worker can emit `<link>` tags in `<head>` and allowlist the host. |
| D7 | Slides split on `---`; per-slide metadata in HTML comments | Per-slide `---` frontmatter blocks are ambiguous: after splitting, a body line like `Note: this matters` is indistinguishable from metadata. This is the Marp convention and renders cleanly on GitHub. Supersedes the earlier intent of literal frontmatter blocks; the coordinates stay just as explicit. |
| D8 | The camera is one transform on a plane | Replaces the mockup's `staging`/`busy`/`exitTo`/`prev` state machine and double-`requestAnimationFrame`, which exist to work around React re-render, not because the motion needs them. |
| D9 | Cell spacing is `viewport + card`, not `viewport` | See §8.1. This is an invariant, not a tuning value. |
| D10 | Glyph wallpapers are generated by a Worker route | Hand-authored SVG data URIs are unusable in practice. |

## 6. Deck file format

    ---
    title: SDKs people don't hate
    date: 2026-09-12
    venue: SomeConf
    summary: Shown on the index and used as the meta description.
    fonts:
      - Instrument+Serif:ital@0;1
      - IBM+Plex+Mono:wght@400;500
    ---

    ```css theme
    .deck { --card:#faf6ee; --ink:#1c1a16; --accent:#c8672c; }
    .deck-backdrop::before {
      background-image: url("/deck/pattern.svg?g=%F0%9F%9A%80&size=54");
      --wallpaper-angle: -15deg;
      --wallpaper-drift: 90s;
    }
    ```

    <!-- pos: 0,0 -->
    <!-- kicker: 01 — Welcome -->

    # Slidecard

    Slides live on a 2D map, and the camera flies between them.

    ---

    <!-- pos: 1,0 -->

    # A tree of slides

### Grammar

    deck        := [deckFrontmatter] [themeBlock] slide (slideSep slide)*
    deckFront   := "---" NL keyvals "---" NL      -- only if the file starts with "---"
    themeBlock  := "```css theme" NL cssText NL "```"
    slideSep    := a line matching /^---$/
    slide       := slideMeta* markdownBody
    slideMeta   := /^<!--\s*([a-z][a-z0-9_]*)\s*:\s*(.*?)\s*-->$/

Frontmatter is a deliberately small YAML subset: `key: value` scalars, and
lists as `- value` lines. No nesting, no anchors, no dependency. Anything
else is a validation error rather than a silent misparse.

Recognised deck keys: `title` (required), `date`, `venue`, `summary`,
`fonts` (list).
Recognised slide keys: `pos` (required), `kicker`, `id`.

## 7. Parsing

Strictly ordered; each step consumes its input before the next sees it.

1. If the file starts with `---`, take the deck frontmatter.
2. Extract the first ` ```css theme ` fence; remove it from the source.
3. Split what remains on `/^---$/m` into slides.
4. Per slide, consume leading `<!-- key: value -->` comments as metadata.
5. Pass the remaining body to the existing `renderMarkdown(src)`.

Steps 2 and 3 must precede step 5. Two reasons, both load-bearing:

- `src/blog/markdown.js` `HR` matches `---` and would render `<hr>`.
- Its `FENCE` info-string capture is `([A-Za-z0-9_+-]*)\s*$` — a single
  token, no spaces — so ` ```css theme ` does **not** match and would fall
  through as a paragraph. Harmless only because the theme block is always
  removed first. §11 pins this with a test.

### 7.1 Authoring traps this parse order creates

Verified against `src/blog/markdown.js` on 2026-08-21, found by baseline
testing. All three fail silently and none were in the original draft.

- **A bare `---` inside a fenced code block splits the slide.** Step 3 runs on
  raw text, before any fence is understood. A two-slide file demonstrating
  YAML frontmatter in a fence parses as four slides.
- **`----`, `-----`, and ` ---` (leading space) do not split.** `HR` in the
  renderer matches `{0,3}` leading spaces and runs of 3+ of `-`, `*`, or `_`,
  while `slideSep` is exactly `/^---$/`. The surplus forms render as an `<hr>`
  inside the slide instead. `***` is the recommended spelling for an
  intentional rule, since it cannot be misread as a botched separator.
- **`# Title` in a slide body renders `<h2>`, not `<h1>`.** The renderer
  shifts headings down one level ("the page already owns the `<h1>`"), so the
  deck page must supply an `<h1>` for the outline to be valid. The §6 example
  does not say this.

The validator in `.claude/skills/writing-slidecard-talks/validate.mjs`
enforces all three and runs without the framework.

`registry.js` parses **lazily per slug** and memoises in a module-level Map.
Eager parsing at module scope would let one malformed deck break the whole
Worker. The index reads frontmatter only.

## 8. The player

### 8.1 Camera geometry (invariant)

The card is capped at `min(880px, 84vw, 128vh)`, so on a wide screen it is
far narrower than the viewport. If cells were spaced one viewport apart,
both neighbours would be visible mid-flight with a band of wallpaper
between them — on a 2560px display with an 880px card, at the halfway point
the outgoing card's right edge sits at x≈440 and the incoming card's left
edge at x≈2120.

With viewport `V`, card `C`, and spacing `S`: the outgoing card clears the
left edge at `t > V/2 + C/2`; the incoming card first intrudes at
`t > S − V/2 − C/2`. Requiring the first before the second gives:

> **S ≥ V + C**

This is what the mockup's `translate(calc(-50vw - 51%))` bought implicitly.
Here it is explicit, and because `--card-w` is one declaration feeding both
the card and the spacing, it holds at every viewport size by construction
rather than by maintained breakpoints — including the `128vh` cap that
governs short, wide projector aspect ratios.

    .deck--player .deck-plane {
      --card-w: min(880px, 84vw, 128vh);
      --card-h: calc(var(--card-w) * 9 / 16);
      --step-x: calc(100dvw + var(--card-w) + 4vmin);
      --step-y: calc(100dvh + var(--card-h) + 4vmin);
      transform: translate(calc(var(--cam-x) * var(--step-x) * -1),
                           calc(var(--cam-y) * var(--step-y) * -1));
      transition: transform var(--fly, 600ms) cubic-bezier(.32,.72,.24,1);
    }
    .deck--player .slide {
      position: absolute;
      left: calc(var(--x) * var(--step-x));
      top:  calc(var(--y) * var(--step-y));
      inline-size: 100%; block-size: 100%;
      display: grid; place-items: center;
      content-visibility: auto;
    }

`dvw`/`dvh` rather than `vw`/`vh` so collapsing mobile browser chrome does
not shift the map mid-flight. `4vmin` is anti-subpixel slack.

### 8.2 What the script does

Adds `deck--player` to the article, reads `data-pos` off each slide into
`--x`/`--y`, and thereafter sets exactly two custom properties: `--cam-x`
and `--cam-y`. All geometry is CSS.

### 8.3 Input

- Arrow keys: nearest slide sharing the current row or column on that axis.
- Space / Shift+Space: document order, forward and back.
- PageDown / PageUp: same as space. **Presentation remotes send these**,
  which is most of what "present from it in a pinch" requires.
- `f` toggles fullscreen. `Escape` leaves the player and restores reading mode.
- The hash tracks the current slide (`#s3`) so a deck can be resumed or
  deep-linked mid-talk.
- The mockup's keycap bar and portrait rotate-veil are both carried over.

## 9. Theming and wallpaper

Deck CSS is injected in a `<style>` after the site stylesheet, on that
deck's page only. It is **unscoped by design**: the blast radius is one
full-bleed page, so no scoping machinery is built. `</style` is escaped.

`.deck-backdrop::before` ships pre-built as an oversized, overflow-clipped,
rotated layer driven by `--wallpaper-angle`, so angled tiles do not show
bald corners. Drift animates `transform`, never `background-position`.
All deck motion — camera included — is wrapped in `prefers-reduced-motion`,
which matters more than usual here because a motion-sensitive reader would
otherwise get the camera and a drifting wallpaper at once.

A deck with no `css theme` block inherits the site's tokens and makes zero
external requests.

Static images live in `public/decks/<slug>/` and are referenced normally;
`[assets] directory = "./public"` already serves them.

### 9.1 `/deck/pattern.svg`

The only place in this design where a request parameter is reflected into a
response body, so it is treated as hostile input regardless of who authors
the callers.

- `g` — the glyph. Required, 1–8 code points, XML-escaped, control
  characters rejected.
- `size` — integer, 8–256, default 48. Non-numeric rejected.
- `opacity` — number, 0–1, default 0.06.
- `color` — optional `#rgb` / `#rrggbb`, for non-emoji glyphs.
- Response: `image/svg+xml; charset=utf-8`,
  `Cache-Control: public, max-age=31536000, immutable`,
  `X-Content-Type-Options: nosniff`.

**Known risk.** SVG used as a background image renders in secure static
mode, and text/emoji rasterisation there is not uniform across engines.
Verify in Safari, Chrome, and Firefox during implementation. Documented
contingency: server-render a real DOM tile layer (a rotated, overscanned
grid of glyph spans) instead, which rasterises exactly like text everywhere
and survives with JS off, at the cost of a few hundred nodes and a
frontmatter field to declare the glyph.

## 10. Validation

Enforced by tests, which are the gate before deploy:

- every slide has `pos`, parsing to a pair of integers;
- no two slides share a `pos`;
- `title` is present;
- `fonts` entries match `^[A-Za-z0-9+:;@,._-]+$` and are URL-encoded per
  family when the `<link>` is built;
- unknown frontmatter or slide keys are an error, not a silent ignore.

D3 traded automatic coordinates for control; this section is the cost of
that trade being paid explicitly rather than discovered on a projector.

## 11. Tests

Against the existing `node --test test/*.test.mjs`:

- **parse** — frontmatter subset, theme extraction, slide splitting,
  comment metadata, and specifically that the theme fence never reaches
  `renderMarkdown` (§7);
- **validate** — missing `pos`, duplicate `pos`, malformed pairs, unknown keys;
- **pattern** — escaping, clamping, rejection, headers;
- **render** — a no-JS smoke test asserting every slide's text appears in
  the server HTML. This is the guard that keeps D1 true as the player grows.

## 12. Routing and docs

Added to `src/worker.js`: `/talks`, `/talks/<slug>` (unknown slug → 404),
and `/deck/pattern.svg`. Everything else keeps 404-ing.

`/deck/pattern.svg` sits outside the `/talks` namespace it serves. Accepted
as-is: it is referenced from CSS, not navigation.

README gains a `/talks` route row, a deck-format section, and one
correction — "no client JavaScript" becomes "no client JavaScript
required", which is accurate rather than quietly false.
